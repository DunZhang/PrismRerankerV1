# Reranker SFT 模型评估结论与推荐做法

## 一、评估方法

- 对两个 SFT 模型各取 ~100 条 yes 样本（annotated_label=yes 且有 contribution/evidence）
- 逐条人工审查 evidence 的忠实度、覆盖度、精简度、contribution 质量
- 用 GAP 值衡量"距离完美还有多远"：
  - GAP=0：已完美，RL 难提升
  - GAP=1：轻微瑕疵
  - GAP=2：明显可改进
  - GAP=3：严重问题（幻觉/偏题/退化）

## 二、两个模型对比

| 等级 | Model 1 (88条) | Model 2 (105条) |
|---|---|---|
| GAP=0 已近完美 | ~39% | **52.4%** |
| GAP=1 轻微瑕疵 | ~22% | 35.2% |
| GAP=2 明显可改进 | ~17% | **10.5%** |
| GAP=3 严重问题 | ~4% | **1.9%** |

Model 2 在所有维度上都更好，尤其是长文档抽取能力（17000 字的文档能精准定位关键信息）。

## 三、Model 2 的系统性问题

### 严重问题（只有 2 条）

1. **幻觉 + 生成退化**：doc 是乱码时，模型不拒答，反而输出 10 次相同书名
2. **知识补全**：doc 信息不全时，模型从训练数据补充了原文没有的事实

### 更普遍的问题（GAP=1/2）

1. **精简度不够**：evidence 常常是 doc 50-80% 长度的改写，没真正压缩
2. **偏题**：query 问"简单解释"给了详细列表；query 问"怎么写新闻稿"给了平台介绍
3. **语种不一致**：query 是小语种（德语、菲律宾语）时，evidence 有时滑回英语

## 四、核心结论：不建议现在上 RL

### 理由一：提升天花板不高

Model 2 只有 12.4% 的样本有明显改进空间（GAP≥2）。RL 最多能"抓"这部分。

### 理由二：剩余问题 RL 大多抓不到

- **精简度问题**：reward 调长度惩罚很容易失衡——压太狠丢信息，压太松没效果
- **偏题问题**：需要 query-evidence 语义对齐，LLM judge 的这个维度打分粒度本身就粗
- **生成退化（乱码输入时重复循环）**：采样问题，RL 可能让它更严重
- **知识补全（doc 不全时编内容）**：规则检查比 RL 更直接

### 理由三：成本/收益不划算

RL 流程复杂（GRPO pipeline、reward 模型、rollout 采样、API 调用）、调参周期长。

相比之下，Model 2 已经 GAP=0 占 52%，再花三个月做 RL 把它推到 60% 的 GAP=0，ROI 很低。

## 五、推荐做法（按优先级）

### 优先级 1：加规则 gate（一周内能做完）

在现有 evaluate 模块基础上加几个硬规则，把"严重问题"兜住：

**a) 幻觉 gate（沿用你已有的 entity_fidelity）**
- 规则：`entity_fidelity < 0.9` → 该样本 reward/score 强制为 0
- 能抓住 idx=48 这类"从外部知识补内容"的幻觉

**b) 重复检测 gate**
- 规则：evidence 中 n-gram（比如 6-gram）重复率 > 30% → 标记为退化
- 能抓住 idx=73 那种"输出 10 次同一个书名"的生成退化

**c) 长度比例 gate**
- 规则：`len(evidence) / len(doc) > 0.7` → 标记"未做真正压缩"
- 能抓住精简度不够的样本

### 优先级 2：SFT 数据侧优化（两到三周）

从 audit 结果里挑出 GAP=2 的样本（约 10-20% 的量），人工改写成更好的参考答案：

1. 把冗长 evidence 精简到原来的 1/2
2. 针对"简单解释"类 query 给精简版
3. 确保小语种 query 的 evidence 用原语种

用这 200-500 条增量样本做一次增量 SFT，大概率比 RL 更直接。

### 优先级 3：下游指标监控（持续）

真正能告诉你"要不要 RL"的指标不是 judge 分数，而是下游效果：

- 人工抽检合格率（每批随机抽 50 条让评审员打通过/不通过）
- RAG 最终答案质量（用 evidence 生成的答案比不用 evidence 好多少）

如果以上两个指标持续卡在某个水平，SFT 数据优化也推不动，**那时再考虑 RL**。

### 优先级 4：RL（暂缓）

如果真的走到这一步，重点不在 reward 设计（你的 9 维已经够细），而在：

- 采样多样性（避免 rollout 全都长得一样）
- reward 的 binary 化（把"evidence 忠实度几分"改成"有没有幻觉 yes/no"，区分度更高）
- 小规模快速迭代（先 1 个 epoch 看效果，不要一上来训满）

## 六、一句话总结

**Model 2 已经好到 RL 收益边际很小的状态了，先把规则 gate 和 SFT 数据补齐，RL 暂缓。**
